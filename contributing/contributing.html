Contributing content

Author

Tim Sherratt

Abstract
This section provides information for people wanting to add content to this guide.
Keywords

Quarto, documentation

Quarto

This site is built using Quarto. Quarto takes a collection of Markdown files and Jupyter notebooks and renders them as a static HTML site. The Jupyter notebooks can include code cells that are executed at build time to generate tables, visualisations and other outputs.

Local development

If you want to contribute new notebooks to the data guide you should set up a local development environment:

  1. install Quarto
  2. create a fork of this Github repository
  3. git clone your forked repository
  4. create a Python virtual environment
  5. install the Python requirements
  6. create/edit notebooks in Jupyter Lab
  7. preview using Quarto
  8. push changes back to the repository

Create a fork of the Data Guide repository

Go to the RAPID Data Guide repository in GitHub and click on the Fork button. Then in the pop-up click Create fork.

There’s more information about forking in the GitHub documentation.

Clone your forked repository

Go to your newly-forked repository, click on the Code button and copy the web url. Then from the command line run:

git clone <web url of your fork>

There’s more information on cloning a repository in the GitHub documentation.

Create a Python virtual environment

There are a number of different tools and methods used to create Python virtual environments. I mostly use pyenv to manage different Python versions and pyenv-virtualenv to create virtual environments. Assuming you’ve installed both of these, and used pyenv to install Python 3.12, you can create and activate a virtual environment like this:

cd rapid-data-guide
pyenv virtualenv 3.12 rapid-data-guide
pyenv local rapid-data-guide

Once this is done, the virtual environment will be automatically activated anytime you enter the rapid-data-guide directory.

Install requirements

You can install the current set of pinned requirements using pip:

pip install -r requirements.txt

If you’re creating new notebooks, you might want to add additional Python packages. In this case you’ll need to update the requirements.in and requirements.txt files. I use pip-tools to manage dependencies and generate the requirements.txt file. First, edit requirements.in to add the new package name/s. Then generate the requirements.txt file by running:

pip-compile requirements.in

You can also use pip-tools to install packages:

pip-sync requirements.txt

Make sure you include the updated files when you push your changes back to the GitHub repository.

Create/edit notebooks

Before you start making changes, it’s a good idea to create a new git branch to work in, for example:

git checkout -b my-new-notebook

Then start Jupyter Lab with:

jupyter lab

See the author guide for some hints and tips.

Preview using Quarto

To preview the rendered site, run:

quarto preview

This will automatically update as you make changes to the files. If your changes aren’t showing up, or you’re getting strange errors, try stopping the preview with Ctrl-CCtrl-C and then restarting.

Adding your changes to the repository

Once you’ve made your changes, you need to commit them.

git add .
git commit -m "Add my new notebook"

Then you can push your updated branch back to Github:

git push origin my-new-notebook

Your changes are now in your forked repository, to add them to the main rapid-data-guide repository, you need to create a pull request.

Profiles

Two profiles are defined dev and prod. The dev profile is the default, it displays all draft pages and includes a warning on the home page that this is the development site. The prod profile removes any draft pages from the site.

You can specify which profile to use by adding the --profile parameter to the quarto preview, quarto render or quarto publish commands. For example to see what the prod site will look like, enter quarto preview --profile prod at the command line.

You can also use the profiles to selectively include/exclude markdown content. For example the homepage dev site warning is wrapped in a .content-visible when-profile="dev" block:

:::: {.content-visible when-profile="dev"}
::: {.callout-warning}
This is a development version of the site and is not intended for public use.
:::
::::
